## Token原因与限制

本机模型目录：deepseek-v4.1-flash默认high推理，输出上限128000；正式调用包装只设置max-turns=4。目录能力表中的low映射为null，不能把传入--effort low视为已成功降低真实推理。
本轮每次请求6000输出上限确实生效，但MAX_THINKING_TOKENS=2048没有按预期限制推理：D家两次纯推理响应分别耗6000、5999，第三次响应4917（其中4310推理），供应商累计输出16916。最终JSON只有1041字符。这证明高开销不是最终ID列表长度，也不是把重复用量字段简单相加。
CLI把length结束且只有推理、没有正文的响应归为可重试空流；这类自动恢复独立于普通网络重试。max-turns不等同于HTTP请求总次数。
首版流式计数还存在格式适配问题：stream-json的可见usage位于message.usage，且部分失败尝试只在最终汇总出现；人鱼汇总输出18902超出18000期望。因此本轮不能宣称整体预算守卫已通过。
隔离调用器现已适配message.usage、核验最终汇总，并加入CODEBUDDY_EMPTY_STREAM_RETRY_MAX_ELAPSED_MS=1。安装包重试判定函数检查通过，但对D家原测试输入的单次真实验证仍报告56112输入、18643输出，超出单请求6000预算，并被最终累计用量检查判失败。该开关不足以控制真实调用总消耗，具体未受控恢复路径尚未定位，不能把源码局部检查当作实际预算保证。[源码函数验证](cost-policy-check.json) · [真实费用验证](cost-guard-live/result.json)。没有修改已安装CLI或用户全局设置。

本轮已返回的7份独立响应累计报告input_tokens=259845，output_tokens=92992，合计352837。另有首次人鱼超时和调整期间中止调用未返回完整用量，实际消耗不能按上述合计封顶。复制缓存不重复计数；没有据此估算未经核实的费用。
